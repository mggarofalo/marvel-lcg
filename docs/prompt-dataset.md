# The prompt dataset

`datasets/digest/prompts.json` is the acceptance fixture for the half of the
fold's return value that nothing else records.

```
(state, input) -> (state, Prompt?, GameEvent[])
                   ^^^^^  ^^^^^^^
     digest/vectors.json  digest/prompts.json
```

Generated by `py_src/tools/digest/emit_prompts.py`. Byte-gated by `--check`, like
the other six (`py_src/tools/fixtures.py`).

## Why it exists

`vectors.json` records the board at every step and says nothing about what the
player was being asked. **A port can reproduce all seven recorded boards of
`rhino / spider_man / 12345` while asking entirely the wrong questions**, because
declining a prompt that should never have been offered leaves exactly the same
board as declining the right one. The recording is generated under a policy that
declines everything, so this is not a hypothetical: it is the normal case.

The two files come out of the same three games, with the same seeds and the same
policy, so **step *n* here is the prompt that was open at step *n* there**.
`emit_prompts` imports `CASES` from `emit_vectors` rather than repeating it. The
step counts are checked against each other in `unit_test/test_prompt_dataset.py`
as an independent consequence, since neither emitter copies them from the other.

## What a prompt is, in the Python engine

`Controller.ChoiceOne` renders each candidate `Effect` into an
`EffectDescriptor` and hands the batch to the device as an `AskOptionPayload`.
That payload is the prompt; `DeviceManager.DoGetInput` supplies the seat it was
put to.

The projection is `tools.affordances.verify.Project` widened to every field the
C# records carry — **twelve of the payload's fourteen**. The two it drops,
`select_rule_param` and `pay_size_is_effect`, are the two MARVEL-161 dropped
after the census, and they are dropped here for the same reason rather than as a
second decision. `test_the_two_vestigial_fields_do_not_survive` names them so
re-adding one is deliberate.

| Payload | C# |
|---|---|
| `event_name` | `Prompt.Trigger` |
| `ability_type` | `Prompt.Kind` |
| `prompt_text` | `Prompt.Label` |
| `show_cancel` | `Prompt.Cancellable` |
| `id` | `Affordance.Id` |
| `name` | `Affordance.Verb` **and** `Affordance.Label` |
| `bind_id` | `Affordance.AnchorId` |
| `bind_player_id` | `Affordance.AnchorPlayer` |
| `failure_reason` | `Affordance.Illegal` |
| `all_legal_targets`, `target_num_range`, `target_groups`, `target_must_include_traits`, `select_rule`, `is_search` | `TargetRequest` |
| `target_payment` | `CostOption[]` |

## Three things this measured that were previously assumed

**`ability_type` is `TimingPriority.name`, and that enum has twelve members** —
`Rule`, `Statistics`, `Constant`, `Status`, `ForcedInterrupt`, `Interrupt`,
`Boost`, `ForcedResponse`, `Response`, `Normal`, `Consequential`, `End`. The C#
`PromptKind` has four, drawn from a census that observed exactly four. **That is
a sample, not a domain.** The fixture's `kinds` index records which ones these
three games reach — `Normal` 25, `Interrupt` 4 — so the gap is visible rather
than inferred, and `PromptKind` will have to grow before a corpus replay is
meaningful.

**An affordance has one string, not two.** The C# `Affordance` carries both
`Verb` and `Label`; the payload carries one `name` and there is no second source.
A port that fills `Label` from anywhere but `name` is inventing it.

**A target request is absent, not empty, when there is nothing to choose.**
`Change_Form` is the case: no candidates, no groups, a `[0, 0]` range. The C#
type is nullable and a client that rendered "select between 0 and 0 things" would
be wrong in a way an absent request cannot be.

## What the milestone game asks

`rhino / spider_man / 12345`, the board the C# port is accepted against. The
fixture asks for twenty steps; the recording holds **seven**, because the policy
declines everything and the game is lost in round three.

| Step | Trigger | Label | Cancel | Affordances |
|---|---|---|---|---|
| 0 | `WhenPlayerChooseAbility` | `Spider-Man resolves mulligans` | no | `Resolve Mulligans` |
| 1 | `WhenPlayerInTurn` | `\n--- Spider-Man's Turn (1) ---` | yes | `Change_Form`, 4 × `Play` |
| 2 | `End Turn` | `Spider-Man End Phase` | no | `End Phase` |
| 3–6 | steps 1–2, for rounds 2 and 3 | | | |

Read against the engine's own console log, the structure is:

```
Spider-Man resolves mulligans          <- step 0
=== Round 1 Start ===
--- Player Phase ---
--- Spider-Man's Turn (1) ---          <- step 1
--- Spider-Man Turn End ---
Spider-Man End Phase                   <- step 2
--- Player Phase End ---
--- Villain Phase ---                     the board moves, once
```

Three notes on that table, all of them things a port gets wrong quietly:

- **`End Turn` is not spelled like the other two triggers.** It is a message
  name where the others are timing points. Recorded as measured, not
  regularised.
- **The label keeps its whitespace**, leading newline included. Two
  implementations will normalise it two different ways.
- **The candidate list is the hand in its own order** — `[42, 45, 37, 9, 47, 46]`,
  which is the `HandsArea` read bottom to top and is not sorted. Sorting it
  changes which card a client highlights first.

## What the C# fold covers, and what it does not

`Marvel.Rules.Fold.Game` implements **the player phase for a player who
declines**: the three prompt shapes above and the transitions between them.
`Game.DerivedVerbs` is the set it builds from state alone —
`Resolve Mulligans`, `Change_Form`, `End Phase`.

`tests/Marvel.Content.Tests/Fold/PlayerPhaseTests.cs` holds it against both
fixtures for steps 0, 1 and 2, and pins the gap as a set rather than a count:
the verbs the recording offers minus `DerivedVerbs` is exactly `{Play}`, so a
verb appearing that nothing derives fails the build.

**Affordance ids are not compared, and must not be.** They are session handles —
the Python engine allocates effect object ids, and MARVEL-164 measured nine of
5,809 recorded inputs drifting, every one exactly 25 too high. `(AnchorId, Verb)`
is the durable key and resolved all nine uniquely. The C# fold *implements* the
property the recording has — handles are cached on `(verb, anchor)`, so a
re-offered option keeps its id, which is why `End Phase` is id 1 at recorded
steps 2, 4 and 6 rather than three different ids — but **that half is not
tested, because nothing is offered twice before the villain phase.** What is
tested is that distinct options do not collide onto one handle, and that two
identically dealt games hand out identical ones.

### Why three steps is more than it sounds

The seven recorded steps are only **three distinct boards**: 0, 1 and 2 are one
board, 3 and 4 another, 5 and 6 a third. A declining player moves nothing, and
the board only changes in the villain phase. So the fold produces three of the
seven recorded digests, and **two transitions remain**.

`TheRecordingReallyDoesHoldOneBoardForThreeSteps` pins that premise. Without it,
a C# board that never changes would keep passing against three recorded boards
that also happen to be equal, for the wrong reason.

### The boundary

Folding past step 2 throws `RulesNotImplementedException`, **before touching the
world**, naming two missing rules rather than one:

- the villain phase, which needs the abilities on `01105` and `01186` plus
  whatever puts a Tough on Rhino;
- the hand refill that precedes it. The recorded hand is already full at every
  step, so the trace is identical whether the refill happens before the prompt
  or after it. **This game cannot distinguish the two orders**, and implementing
  it now would pin an order nothing has checked.

## Regenerating

```bash
cd py_src
python -m tools.digest.emit_prompts          # rewrite
python -m tools.digest.emit_prompts --check  # what CI runs
python -m unittest unit_test.test_prompt_dataset
```

It boots the engine and plays three games, so it takes seconds rather than
milliseconds and does not belong in the fast unit tier. The output is byte-stable:
same code, same engine, same file, no timestamps.
