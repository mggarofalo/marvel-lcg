## Priority and limits

1. Finish PR #439 evidence/acceptance and MARVEL-630's additive-content compatibility evaluation. Its merged predecessor migration checks do not close the shared item.
2. Research Green Goblin and Ms. Marvel next. For Green Goblin, the mc02 insert confirms two scenarios/four modular sets and specifies Norman's attack and Goblin's scheme replacements; this is enough to begin a bounded packet, not to assert implementation readiness. The mc05 sheet is descriptive and supplies no complete starter or timing packet.
3. Share prerequisites across later waves: three-form identity (Ant-Man/Wasp), separate game areas (Kang), campaign persistence (large boxes), set-aside/alternate decks (Doctor Strange/Valkyrie), and dynamic encounter composition (Hood). Do not make one generic research issue per pack.

The snapshot contained 32/32 descriptions. Child mapping covered all 32. Plane comment checks covered all 32 (only 560/562 had comments), and explicit link checks covered 559–568, 573, 578, 584, 589 (no external issue links there except PR #439 in descriptions). Relation checks covered those 14 selected items and 581–590; the remaining relation requests were rate limited and their exact blocker sets were not independently verified. No official component count was independently reconciled for untouched packs; the issue's generated face count is an observation only. No card-by-card behavior research or runtime verification was performed for them. Current CI result for PR #439 was not checked.

## Skill feedback from forward use

- The research reference correctly distinguishes inventory pointers from an implementation packet and allows targeted depth. It should explicitly tell an auditor to map the shared prerequisite's *current* state, because the 32 issue relations name MARVEL-630 while its merged predecessor work can make the blocker look resolved.
- It requests a bounded Plane snapshot but comments/links/relations are separate endpoints. Specify a compact evidence capture shape (issue, child IDs, comments, links, relations) and an `Unverified` rule for failed calls; otherwise large audits cause many serial CLI requests and ambiguous absence claims.
- The four readiness labels have no clean state for an implemented PR awaiting CI and owner acceptance. Add `Implementation review` or direct users to label the *next bounded slice* Ready while stating the whole pack is not accepted, as done for 560/562 here.
- The pack issue template is roughly 11–14K characters per untouched issue, largely repeated acceptance text. A short pack-specific research link/status block would make existing evidence and the next executable action easier to find.
